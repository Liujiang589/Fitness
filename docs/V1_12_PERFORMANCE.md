# 独练 V1.12 流畅度检查

2026-10-23，手机22011211C。通过ADB读取Android gfxinfo，用户手动滚动；电脑模拟触控被手机拒绝，未修改安全设置。

## 优化前的首页采样

手机实际安装V1.9 / versionCode23，带DEBUGGABLE标记。确认处于训练首页后清零统计，用户上下滑动并回复完成，读取本次进程的绘制统计：

| 指标 | V1.9手动采样 |
| --- | ---: |
| 绘制帧数 | 2599 |
| 超过系统帧截止时间 | 79帧 / 3.04% |
| P50 / P90帧时长 | 8 / 16ms |
| P95 / P99帧时长 | 20 / 36ms |
| Slow UI thread / Slow draw commands | 73 / 46 |

原始文件保存在本地忽略目录`.local-download/V1.12-home-before-manual-gfx.txt`。清零到读取约75秒，包含用户约15秒滑动及等待期间的应用帧，不是严格固定时长的自动基准。系统另报legacy口径23.05%，不能与这里3.04%的现代帧截止时间口径混用。最初未清零的历史混合采样5.26%也不能充当首页基准。

## 代码中已修正的工作

- 两张1536×1024高清照片改用后台解码、预上传及16MiB LRU缓存，保持原分辨率。没有靠降低图片清晰度获取性能。
- Room数据流先去重，再在Default线程解析JSON与排序。备份的JSON编解码及校验也移到后台，界面线程只更新状态。
- 训练计时由250ms全训练区刷新改为独立表头每秒更新；只在前台运行，恢复时按真实时间刷新。
- 首页只订阅户外运动种类/状态，根界面只订阅是否阻止更新弹窗；速度与时间仍在户外页实时显示。
- 动作列表滚动时停播预览，静态示范缓存姿态并使用独立绘制层；不影响详情的播放和分解。
- 热点列表筛选与周数据复用计算结果。周回顾只在展开时后台计算。
- 交付使用非debuggable的Release变体，开启R8与资源压缩，沿用历史签名，含依赖提供的Compose运行配置文件。

这些是可确认的负载问题及修正，单凭gfxinfo不能把每一帧延迟精确归因给某一项。开发调试包会影响性能测量，也不能断言它是全部卡顿的唯一原因。

## 优化版真机结果

已在连接的22011211C手机上以`adb install -r`覆盖安装成功，未卸载或清除应用数据。系统确认版本1.12/code26、非debuggable；应用启动成功，首页高清照片、入口与静态矢量示范正常显示，旧的“步行待继续”状态仍可见。启动检查时应用进程存活，限定该进程的AndroidRuntime错误日志无FATAL EXCEPTION。没有据此声称全部历史记录已逐项核对。

清零新版绘制统计后，用户再次在首页上下滑动并回复“新版已滑动”，读取时前台仍是独练。新版采样4787帧，23帧超过系统截止时间，比例0.48%；P50/P90/P95/P99为7/9/10/12ms，Slow UI thread为4，Slow draw commands为20，GPU P95/P99为6/7ms。清零到读取约65秒，包含约15秒滑动及等待期间的应用帧。原始记录为本地忽略目录`.local-download/V1.12-home-after-manual-gfx.txt`。

对照旧版同机手动采样：3.04% → 0.48%，P95 20 → 10ms，P99 36 → 12ms。仅能判断本次现场采样明显改善；旧版V1.9调试构建、新版V1.12发布构建及布局均不同，不能把差异归因到某一项代码，也不是固定手势、固定刷新率的受控基准。动作库、长训练列表、地图及大数据历史未取得相同方式的前后采样。


## 如何理解结果

手动滑动速度、帧数、系统刷新率、手机温度和后台应用会影响结果。版本布局也已变化。即便取得前后数据，也只能作为同机现场检查，不能当作严格受控实验或保证所有页面、所有手机无掉帧。当前未引入完整Macrobenchmark或Perfetto逐帧跟踪；长历史、长训练、大字体及持续GPS下仍应按体验清单检查。
